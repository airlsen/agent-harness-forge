# 16 · 会话内向用户提问

> 状态：**已实现**（2026-11-25）。按本文方案落地：Runner（engine / kernel / server）、控制面（工单 kind=question + `/api/agent/questions` 路由 + 加列迁移）、前端（QuestionCard 卡片）、测试（`check-capabilities` 提问 / 超时 / 策略关闭三段、`check-turns` 工具名段）。
> 与方案的差异：提问工具落在平台契约 **base 组**后，旧部署数据库里保存的策略不含该工具，升级后默认关闭，需管理员在治理中心重新保存执行策略（或空间开关）放开——这是刻意的安全默认。
> 上位文档：`docs/14-切换sdk方案.md`（插件归类）、`docs/12-能力构建与场景装配方案.md`（能力下发）。

## 1. 背景与现状

现在系统里有**两种**「停下来等用户」的交互，只有第一种是通的：

| 交互 | 触发者 | 通道 | 现状 |
| --- | --- | --- | --- |
| 工具确认 | dsh（bash 请求突破沙箱、管理员标记需确认的 MCP 工具） | `approval/request` 宿主回调 → 审批票据 → 确认卡片 | ✅ 已支持 |
| 模型提问 | 模型调用 `ask_user_question` 工具 | `user-question/ask` 宿主回调 | ❌ 被引擎写死拒绝 |

`runner/src/kernel/dsh/engine.ts` 里 `onUserQuestion: async () => ({ cancelled: true as const })`：
模型遇到信息缺口（口径、范围、确认选择）时拿到「用户未回答」，只能臆测参数或放弃任务。
这是企业用户最常撞到的洞，也是后续「结构化输入表单」路线的第一步。

## 2. dsh 协议事实（0.2.2-rc.5，已核实）

- **工具**：`tool-ask-user` 插件注册模型工具 **`ask_user_question`**；`user-questions` 插件提供进程内
  `ctx.userQuestions` 接缝并转发到宿主。工具参数：`questions: [{id, question, header?, options?: [{label, description?}], multi_select?}]`（可一批多个问题）。
- **宿主回调**：`DeepSeekHarnessOptions.onUserQuestion(request, { signal }) => Promise<SdkUserQuestionResult>`。
  请求 `request.questions` 的每一项：`{id, question, detail?, header?, options?: [{label, description?}], multiSelect?, intent?}`（注意：模型侧参数是 `multi_select`，线上结构是 `multiSelect`，dsh 自己转换）。
  回复：`{ answers: [{ id, selected: string[], custom? }] }`（**每个问题 id 恰好一项**）或 `{ cancelled: true }`（用户不答/跳过，模型继续自行处理）。
- **取消通知**：运行时撤销挂起问题（回合被中止等）会发 `user-question.cancelled { requestId, sessionId }` 通知；
  `requestId` 不暴露给回调，无法逐 ticket 对应——收到该通知时按「取消本会话全部挂起提问」处理（串行 agent 循环下几乎恒为 1 个）。
- **intent 字段**：`plan-review` / `approval` 两种呈现意图分别来自 `plan-mode` 与 `permission` 插件，二者都在 `SDK_OFF`，
  Forge 只会收到通用问题；防御性处理：不认识的 intent 一律按通用选项卡渲染（协议约定 intent 只改呈现、不改应答编码）。
- **计时模式（timed）**：`tool-ask-user` 另有 `mode:'timed'`（超时转 pending、用户可迟答、`attachWait` 接手等待等一整套投影机制）。
  **一期不用**：Forge 的回合模型与审批语义更贴近 blocking + 内核超时 → `{cancelled:true}`，timed 留给后续。

## 3. 设计决策

| 决策点 | 选择 | 理由 |
| --- | --- | --- |
| 开关归属 | `contracts/platform.json` 加工具 **`ask_user_question`，group `base`**（provider `@deepseek-ai/dsh-tool-ask-user`），契约 version 2 → 3 | 提问是对话基础设施，不是场景可选件：随基础能力默认可用；企业执行策略与空间工具开关天然成为上限（去掉即整块关闭插件，无多余提示词）。todo/goal 那种按场景勾选的路径二期需要时再降级 |
| 插件归类 | `user-questions`、`tool-ask-user` 从 `SDK_OFF` 移入 `SDK_SWITCHED`，按 `allowed` 里是否含 `ask_user_question` 开关 | 与 `tool-fs` 按 read/write 开关同一模式；`user-questions` Config 为空写 `true`，`tool-ask-user` 显式写 `{ mode: 'legacy' }` |
| 超时语义 | 内核计时（新增策略字段 `askTimeoutSeconds`，默认 300 秒）到点回 `{cancelled: true}`；卡片保留显示「已超时」 | 与审批票据同构；提问要打字，比审批的 120 秒长。到期模型继续自主推进，页面上的问题与模型后续处理都在轨迹里可见 |
| 用户跳过 | 卡片提供「忽略」→ `{cancelled: true}`，与超时同码、UI 状态分开 | dsh 语义：cancelled ≠ 拒绝，模型会带着假设继续 |
| 票据存储 | 复用 `ApprovalTicket` 表，新增 `kind` 列（`tool` / `question`，默认 `tool`） | 字段天然对齐（tool=`ask_user_question`、args_digest=问题 JSON、decision_payload=问题+答案+runnerTicketId）；审计、刷新页面恢复、待办查询全部沿用 |
| 回执接口 | Runner：`POST /v1/sessions/:id/questions/:ticket/resolve`；控制面：`POST /api/agent/questions/{ticket}/resolve`（body 为 answers 或 `{action:'cancel'}`） | 与审批路由平行，不复用 `Decision{approve\|deny}` 模型，避免语义混用 |
| 内容校验 | 内核侧钳制而非拒绝：问题 ≤10 条、question ≤2000 字、options ≤20×（label 200 / description 500）、detail ≤4000、custom ≤4000；答案必须覆盖每个问题 id 恰好一次且 `selected ⊆ 原选项` | 校验失败回 422 只会打断用户；模型生成的超长文本钳制后照常呈现。全部内容按纯文本渲染，不做 HTML |
| 中止/重启 | `interrupt()` 与回合 `finally` 里 `cancelQuestions()`（全部回 `{cancelled:true}`）；Runner 重启后挂起提问随进程消失，resume 后该工具调用按 dsh 的未知结果处理 | 与审批票据同一清理路径 |

## 4. 实现步骤

### 第 1 步 · Runner（DSH 适配层 + 内核，约 1 天）

1. `src/kernel/dsh/engine-tools.js`：`ENGINE_TOOLS.ask = 'ask_user_question'`（`engine-tools.d.ts` 同步）。
2. `src/kernel/dsh/runtime-config.ts`：
   - `SDK_SWITCHED` 增 `user-questions: '向用户提问（ask_user_question）'`、`'tool-ask-user': '向用户提问（ask_user_question）'`；
   - `switchedRows`：`if (has(ENGINE_TOOLS.ask)) on['user-questions'] = true, on['tool-ask-user'] = { mode: 'legacy' }`；
   - `SDK_OFF` 注释里划掉「向用户提问」。
3. `src/kernel/dsh/engine.ts`：
   - `EngineHost` 增 `ask(request: { questions: unknown[] }): Promise<AnswerOutcome>`，`AnswerOutcome = { answers: AskAnswer[] } | { cancelled: true }`；
   - `onUserQuestion: (req, { signal }) => host.ask(req)` 替换写死的 cancelled；signal 观察：内核取消挂起提问后 resolve，进程照常关闭。
4. `src/kernel/dsh/protocol.ts`：
   - `translateNotification` 增 `user-question.cancelled` 分支（内部事件，转发内核取消全部挂起提问，不落轨迹）；
   - `SDK_METHODS` 已含 `user-question/ask`，无需改；`contract-check` 会自动覆盖新配置键 `{mode:'legacy'}`。
5. `src/kernel/session-kernel.ts`：
   - `Entry.questions = new Map<ticketId, Pending>`；`requestQuestion(entry, request)`：钳制 → 发 `question_required` `{ticketId, questions, timeoutSeconds}`（source `tools`）→ 等待裁决/超时；
   - `resolveQuestion(id, ticketId, decision)`：校验答案形状（见上表）→ 发 `question_resolved` `{ticketId, action: 'answered'|'cancelled'|'timeout', answers?}`；
   - `interrupt()` / `runTurn` finally 增 `cancelQuestions()`；
   - `boot()` 的 `EngineHost` 接线 `ask`；整轮上限（`RUNNER_TURN_TIMEOUT_SECONDS`）与空闲回收逻辑不变。
6. `src/server.ts`：`POST /v1/sessions/:id/questions/:ticket/resolve`（5 行，仿 approvals 路由）。
7. `src/kernel/manifest.ts` / 契约：`RuntimePolicy` 增可选 `askTimeoutSeconds`（默认 300）→ `make contracts` 重新导出 schema 与
   `manifest.generated.ts`；纯增量字段，`MANIFEST_VERSION` 不动。

### 第 2 步 · 控制面（约 0.5 天）

1. `models/approval_ticket.py`：`ApprovalTicket` 增 `kind` 列（默认 `tool`）。
2. `services/session_service.py` 的 `persist()`：仿 `approval_required` 分支处理 `question_required` / `question_resolved`
   （建票、换算 DB 票据 id、状态 `pending/answered/cancelled/timeout`），同一事务推进 `runner_event_seq`。
3. `routes/` 增 `POST /api/agent/questions/{ticket}/resolve`：body `{answers}` 或 `{action:'cancel'}` → 按
   `decision_payload.runnerTicketId` 转发 Runner；审批的 `Decision` 模型不动。
4. `core/contracts.py` 无需改（组不变）；治理中心执行策略页会自动多出「向用户提问」开关（来自契约目录）。

### 第 3 步 · 前端（约 1 天）

1. `stores/conversation.ts`：`question_required` → `questions[]`（`PROCESS_KINDS` 增两种事件，历史轨迹可见）；
   `question_resolved` / `done` 移除并记录状态；`resolveQuestion(ticketId, payload)` 调新接口。
2. `views/conversation/AgentChat.vue` + 新组件 `components/message/QuestionCard.vue`：
   在运行中的回复下方渲染（与审批卡片同一位置，`v-for` 并发多张）：
   - 每个问题：`header` 标题、`question` 正文、`detail` 辅助文本、`options` 单选（`multiSelect` 时多选）、
     「其他」自由文本（选中自定义时 `custom` 覆盖/补充 `selected`）；
   - 底部「提交」「忽略」；超时/取消后卡片置灰显示状态；**全部纯文本渲染**；
   - 处理中主操作仍是「中止」，问题卡片不抢焦点（对齐 `docs/15` 的不打断原则）。
3. `utils/conversation/toolTitles.ts`：`ask_user_question: '向用户提问'`（过程块与回放显示）。

### 第 4 步 · 测试与文档（约 0.5 天）

1. `runner/scripts/check-capabilities.mjs` 增三段：模型夹具发起 `ask_user_question` → 断言 `question_required`、
   `resolveQuestion` 后工具结果携带所选 label；超时路径断言回 `{cancelled:true}` 且卡片事件为 `timeout`；
   策略去掉 `ask_user_question` 后断言 runtime patch 里两个插件 `disabled:true`。
2. 前端 `check-turns.mjs` 增提问卡片状态用例；`check-business-api.py --browser` 手工回归：提问 → 回答 → 模型继续。
3. 文档：`docs/14` 表格与「第 5 步」划掉向用户提问；`CLAUDE.md`、`README.md` 工具清单补一行；本方案补验收记录。

## 5. 边界与已知取舍

- **requestId 无法对应**：`user-question.cancelled` 只能整会话取消挂起提问；串行循环下实际恒为 1 个，注释说明即可。
- **多问题并发**：多工具并行时可能出现多张卡片，票据表与 UI 已按 N 条挂起设计。
- **Runner 重启中的提问**：不持久恢复（与审批一致——审批行会标 cancelled，提问因进程消失随回合失败结算）。
- **费用**：提问本身是工具调用，不产生额外模型请求；timeout 后模型继续跑，消耗与现在「瞎猜」路径相同或更省。
- **timed 模式**（超时后用户仍可迟答、问题转新一轮）：一期不做，留待「结构化输入表单」一起设计。
