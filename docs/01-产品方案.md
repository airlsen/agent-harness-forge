# 企业级 Agent 平台（基于 DeepSeek Harness）· 产品方案

> 版本：v1.0（2026-11-17）
> 定位：在 DeepSeek Harness（dsh，MIT 开源、插件化 Agent Harness）之上，构建面向企业的多租户 Agent 平台。
> 与旧 AgentX（Claude Agent SDK 版）的关系：继承「场景配置驱动执行」的产品思想，但用 dsh 的插件体系重构底层。

---

## 一、背景与机会

### 1.1 为什么是现在、为什么是 dsh

2026 年 Agent 工程的核心共识是 **Agent = Model + Harness**：模型负责推理，Harness（提示词装配、工具执行、上下文管理、会话、沙箱、编排）决定 Agent 是否真的"能干活"。LangChain 的实验证明：模型不变、只调 Harness，Terminal Bench 得分可从 52.8% 提升到 66.5%——**Harness 是企业的差异化资产，而模型是可替换的耗材**。

DeepSeek Harness（2026-08-13 开源，MIT 协议）是这个范式下对企业最友好的底座：

| 特性 | 对企业的意义 |
|---|---|
| **Everything is a plugin**（基于 Cordis 元框架） | 模型、工具、技能、会话、沙箱、存储、循环调度、UI 全部是可插拔插件，企业定制 = 挂插件/写 patch，**不需要 fork 源码** |
| **模型无关（model-agnostic）** | 默认 DeepSeek V4 Pro 一等公民（国产、可私有化部署、成本极低），也可接 GLM/Kimi/Qwen/自托管 vLLM，甚至保留 Claude 作为高端兜底——**不被任何模型厂商锁定** |
| **Session Log 是不可变事实源** | 模型看到的一切都写入 append-only 日志（系统提示词、思维链、工具调用与结果、子代理派发、上下文注入），resume/fork/replay 共用同一事件流——**这就是企业审计梦寐以求的全链路留痕** |
| **MIT 协议 + 可完全私有化** | 金融、政企、医疗等强监管行业可过安全评审 |
| **四种运行模式（Standard / PTC / Minimal / Creative）** | 天然覆盖"日常任务 / 批量自动化 / 模型评测 / 场景编排"四类企业诉求 |

而旧 AgentX 的 Claude Agent SDK 路线的痛点恰恰是：闭源模型成本高、Claude Code CLI 是黑盒（hooks/MCP 之外不可定制）、企业数据要出域、审计能力要靠自己硬补（PostgresSessionStore 镜像 transcript）。

### 1.2 诚实面对风险（写在最前面）

dsh 当前是 **Developer Preview（v0.1）**，官方明确"会有兼容性破坏变更，核心插件与基础接口将快速迭代"。因此本平台的第一架构原则是：

> **平台永远不修改 dsh 源码，所有企业能力以 Cordis 插件、profile patch、bundle 的形式挂载；同时执行内核在平台侧抽象为接口，dsh 是可替换实现（备选：deepagents / Hermes Agent）。**

### 1.3 与 Dify / Coze / 低代码平台的定位差异

| 维度 | Dify / Coze 类 | 本平台 |
|---|---|---|
| 产品基因 | 低代码工作流编排（LLM 是画布上的一个节点） | **Agent 运行时平台**（Agent 是一等公民，自主规划+工具执行） |
| 适用任务 | 确定性流程、表单驱动自动化 | 长周期、多步骤、目标驱动的非确定性任务（代码、研发、数据分析、报告） |
| 定制方式 | 画布拖拽 + 插件 | 场景（Bundle）= 能力声明 + 提示词 + 策略，插件可深入到 Harness 任何一层 |
| 治理深度 | 开源版 RBAC/审计弱，企业版昂贵 | 从 dsh Session Log 原生长出的全链路审计 + 自研控制面 |

一句话定位：**企业的"数字员工运行与治理平台"——业务人员用场景干活，开发者用插件扩展，管理员用审计与策略兜底。**

## 二、角色与核心用户

| 角色 | 诉求 | 平台提供的核心界面 |
|---|---|---|
| **业务用户**（产品/运营/测试/分析师） | 不懂技术，选场景、填需求、拿结果、可追溯 | Agent 工作台、场景中心 |
| **场景作者 / Agent 开发者** | 把团队 SOP 沉淀为可复用场景与技能 | 场景编辑器（AI 生成 + 手动）、技能/插件开发台、Creative 模式调试 |

| **平台运维 / 审计员** | 安全合规、故障排查、成本分摊 | 审计中心（Trajectory 回放）、可观测大盘 |
| **平台管理员** | 内核版本、插件市场白名单、全局策略 | 平台管理（内核、插件注册表、许可证） |

## 四、核心产品抽象（三个概念的重新定义）

旧 AgentX 的核心抽象是「场景 = 能力声明 + 提示词模板」，这个思想保留并升级：

| 抽象 | 旧 AgentX 定义 | 本平台定义 |
|---|---|---|
| **场景（Scenario）** | promptTemplate + skills/MCP/工具/项目/模型 | 场景 = **Bundle**（插件集合 + profile patch + 系统提示词分区 + Skill 文件 + 治理策略 + 模型路由 + 输入契约 inputSchema），可版本化、可上架 |
| **会话（Session）** | 常驻 CLI 进程 + PG transcript 镜像 | 会话 = dsh append-only **Session Log**；续聊/分叉/回放/检索共用同一事件流；天然支持审计重建 |
| **能力（Capability）** | Skill / MCP / 内置工具三类 | 能力 = **插件**，且分层：模型适配器（ctx.llm）/ 工具（ctx.tools）/ 技能（Skill 包）/ MCP / 沙箱与存储（ctx.sandbox/ctx.fs）/ 调度（ctx.jobs）——与 dsh 扩展点一一对应 |

**关键产品决策：场景对业务用户是"应用"，对场景作者是"装配单"，对系统是"一组可复现的配置"**。场景选中后必须与执行链路完全解耦（沿用旧设计的约束），新增场景不改执行代码。

## 五、核心功能详细设计

### 5.1 Agent 工作台（P0）

- **执行视图**：流式正文、工具调用卡片（可展开看入参/出参）、产物文件预览、成本实时显示（token/金额）。
- **轨迹视图（Trajectory）**：直接消费 dsh Session Log，按来源过滤（系统提示词/思维链/工具/子代理/上下文注入）。思维链默认折叠，遵守不同模型的 CoT 展示策略。
- **多模式执行**：
  - 标准模式（Standard）——默认，通用任务；
  - **PTC 模式**（程序化工具调用：模型生成一段代码把多轮工具调用编成一次执行）——用于"批量 1000 条数据清洗""全仓库批量重构"这类确定性批量任务，**这是批量任务的产品化入口，替代旧设计的 inputSchema 批跑的粗糙形态**；
  - Minimal 模式——不直接暴露给业务用户，用于平台侧的模型评测基线。
- **人工审批**：沿用旧设计 ApprovalManager 的交互（approve/deny/带参数提交/选择题），但底层换为 dsh 的 tools/* 事件拦截 + 审批桥接插件；支持**超时策略**（默认 deny）与**转为 IM 审批**（P1）。
- **会话分叉与回放**（P0 末期）：从任意轨迹点 fork 出新会话（排查问题、A/B 提示词）；replay 用于演示与回归测试。
- **复核模式**（保留旧设计精华）：执行助手 ↔ 复核助手多轮循环，复核模型可与执行模型不同（如执行用 V3.2 非思考省钱，复核用 V4 Pro 思考模式），输出「复核通过」提前终止。

### 5.2 场景中心（P0）

继承旧方案的交互骨架（选择器 + 配置抽屉 + 双模式生成），做三处升级：

1. **智能生成升级为"Creative 模式驱动"**：旧方案是后端拼 prompt 调模型生成 JSON 草稿；新方案直接调一个 dsh Creative 模式的 Agent——它能在内存里试装插件、验证能力组合可用性后再产出场景装配单，生成质量与可执行性远超"凭目录脑补"。
2. **三级分发体系**：
   - 官方场景（平台预置，只读，可复制）；
   - 我的场景（个人 CRUD，沿用旧方案）；
   - **团队场景空间**（P1）：发布到部门空间需经"场景上架审批"（租户管理员/场景治理员审核：提示词合规、能力权限是否越界、成本预估），审批通过部门内可见可用——这是旧方案明确"本期不做"的，但企业场景必须有分发与准入。
3. **场景版本化**（P1）：每次发布产生不可变版本 v1/v2/…；使用中场景改配置不影响已开始的会话（会话开始时快照场景装配单）；支持回滚。旧方案的"本期不做版本化"在企业审计下不成立。

### 5.3 能力中心（P0 骨架 / P1 完整）

- **插件注册表**：登记每个插件的 npm 包/版本/扩展点/权限声明/审核状态/签名。平台只允许安装**白名单内**的 dsh 插件（企业安全红线：社区插件必须过安全扫描与人工审核）。
- **Skill 库**：Skill = 提示词 + 脚本/资源的包（dsh 的 skills 机制），版本化管理，"把一次成功沉淀为可复用招式"的产品化。
- **MCP 服务目录**：沿用旧设计的 MCP 动态认证思想（每请求注入登录态 headers，不落配置），统一注册、健康检查、按场景授权。
- **内部插件市场**（P1）：开发者提交 → 自动化检查（依赖声明、副作用可回滚、权限用途）→ 安全扫描 → 人工审核 → 上架 → 按场景安装。

### 5.4 模型中心（P0）

- **模型目录**，按用途分层：
  - **主力执行**：DeepSeek V4 Pro / V3.2（thinking + tool-use，复杂 Agent 任务）；
  - **轻量执行**：V3.2 非思考模式（快、便宜，简单问答与格式化任务）；
  - **复核/高危场景**：可配置更强模型交叉复核；
  - **私有化**：企业自部署 DeepSeek（vLLM/SGLang）经 OpenAI 兼容端点接入，数据不出内网；
  - **兜底**：保留任意 OpenAI 兼容外部模型（含 Claude），由策略决定何时允许。
- **路由策略**：场景绑定（作者指定）→ 租户策略（强制私有化/禁外部）→ 成本策略（超预算自动降级到便宜模型）→ 降级链（主模型超时/限流自动切备用）。所有路由由**模型网关**统一执行，dsh 侧只配一个 `ctx.llm` 企业适配器指向网关。
- **成本透明**：每个模型标价（元/百万 token，输入/输出/缓存分开），会话与场景维度实时累计展示。

### 5.5 治理中心（P0 核心项）

- **多租户与组织**：租户 → 部门 → 成员三级；支持从企业现有组织同步（LDAP/飞书/钉钉通讯录，P1）。
- **认证**：SSO（OIDC/SAML/CAS）P0 支持 OIDC；会话管理沿用旧平台的登录态体系。
- **权限模型**：RBAC 为主，关键资源叠加归属人与空间维度：
  - 对象权限：场景（看/用/改/发布）、插件（装/审）、知识库（读/写）、项目代码库（读）。
  - **数据权限继承企业组织架构**（如只能访问本部门项目），在场景装配与工具执行两处强制校验。
- **配额与预算**：三级限额（租户/部门/个人）× 两种度量（token/金额）；超限动作可配（拒绝/降级模型/需审批）。
- **安全策略**（场景级与租户级两层叠加）：
  - 工具策略：禁止/需审批/允许 三级，如 Bash 默认"需审批"、写操作默认限定目录；
  - 网络策略：沙箱出站立白名单（默认仅企业内网与已授权 MCP/模型网关）；
  - 数据策略：敏感信息规则（凭据/PII/内网地址），在输出与日志两处脱敏。
- **审批策略**：按"工具 × 场景 × 数据敏感度"配置矩阵，决定何时必须人在回路。

### 5.6 审计与运营中心（P0 基础 / P1 完整）

这是本平台相对 Dify 类产品的**差异化王牌**，因为 dsh 的 Session Log 有"一切可重建"的运行时不变量：

- **审计查询**：六问可答——谁、什么时候、用哪个场景（哪个版本）、模型看到了什么（完整上下文重建）、调用了什么工具（入参/出参）、花了多少钱。
- **审计回放**：任意历史会话可逐事件回放；监管检查时可导出只读回放链接。
- **合规导出**：审计日志 WORM（只增不改）存储，留存期可配，支持对接到企业 SIEM。
- **运营大盘**：场景成功率 Top/Bottom、人工干预率、成本环比、模型用量分布、缓存命中率——反哺场景作者优化提示词与能力组合。

### 5.7 定时与后台任务（P1）

基于 dsh `ctx.jobs`：场景 + cron = 定时 Agent（每日代码巡检、每周数据周报、监控告警自动初判）。产物推送到工作台与 IM。这是把"对话式工具"升级为"数字员工"的关键一步。

## 六、关键用户旅程

### 旅程 1：业务用户完成一次任务（P0 验收标准）

1. 登录（SSO）→ 工作台 → 场景选择器（官方 + 我所在空间的场景，分组合并展示）；
2. 选中「接口测试代码分析」→ prompt 模板自动填入输入框，改两句话说清需求；
3. 提交 → 流式看到 Agent 思考、读代码、调 MCP 查询接口文档；
4. Agent 要执行 `git push` 类高危命令 → 弹审批窗 → 用户拒绝 → Agent 换方案继续；
5. 完成 → 右侧产物预览 + 本次成本 ¥0.37 → 一键「查看轨迹」留档。

### 旅程 2：场景作者创建一个场景

1. 场景中心「+ 新建场景」→ 抽屉：智能生成（默认）/ 手动装配；
2. 输入自然语言描述 → 后端调 Creative 模式 Agent，**实际试装插件验证可用** → 回填装配单（名称/图标/提示词分区/勾选的插件与 Skill/MCP/模型路由/策略），标记「AI 建议」；
3. 微调 → 「试运行」沙箱验证（必须跑一次成功才能保存，企业场景质量红线）→ 保存到「我的场景」；
4. （P1）「发布到团队空间」→ 上架审批 → 部门可见，生成 v1。

### 旅程 3：审计员追溯一次事故

1. 审计中心按"用户/时间/场景"检索到会话 → 打开轨迹回放；
2. 按来源过滤到 `tools/*` → 定位异常工具调用及其完整入参/出参；
3. 导出审计包（事件流 + 重建的模型请求 + 审批记录）→ 归档。

## 七、范围与版本规划

### MVP（P0，约 10 周）—— 跑通"企业可用的最小闭环"

工作台（标准模式 + 审批 + 轨迹基础视图）、场景中心（官方/我的 + AI 生成 + 试运行）、模型中心（DeepSeek 官方 API + 一个私有化端点 + 场景绑定路由）、治理（SSO-OIDC、RBAC、配额、工具三级策略、脱敏）、审计（查询 + 回放基础版）。**明确不做**：团队空间/上架、版本化、知识中心、定时任务、插件市场、PTC 产品化入口。

### V1（P1，MVP 后 +8 周）—— "企业分发与沉淀"

团队场景空间与上架审批、场景版本化、知识中心（RAG 插件化）、定时任务、内部插件市场（白名单 + 审核流）、MCP 目录完善、IM 审批、成本分摊报表。

### V2（P2，+8 周）—— "规模化与智能化"

PTC 批量任务产品化、多 Agent 协作编排（子代理场景化）、场景质量自动评估（基于轨迹回放的成功样本挖掘）、Skill 自动沉淀建议、执行内核多实现（dsh 之外可切换 deepagents/Hermes 的备选通道，对冲 preview 风险）、跨地域私有化多活。

### 成功指标（北极星 + 护栏）

- 北极星：**周均成功完成任务数 / 活跃用户**（"帮到活"而非"聊了天"）；
- 质量：场景任务成功率 ≥ 70%（按场景分级）、人工干预率逐月下降；
- 成本：单任务平均成本 ≤ 旧 Claude 方案的 1/5；
- 治理：审计覆盖率 100%（每次执行可完整重建）、高危工具 100% 过审批策略；
- 护栏：P0 事故（数据越权/密钥泄露）= 0。

### 明确非目标（沿用并扩展旧方案的纪律）

- ❌ 不做 C 端 Bot 分发与多渠道接入矩阵（那不是 Agent 运行时平台的主战场）；
- ❌ 不做可视化工作流画布编排（与 Dify 正面竞争无意义；确定性流程请客户用 Dify/n8n，本平台与它们可通过 MCP/HTTP 互调）；
- ❌ MVP 不做社区插件自由安装（企业安全红线：白名单制）；
- ❌ 不 fork、不魔改 dsh 源码（插件与 patch 解决一切定制）。

## 八、与旧 AgentX 的承继关系（给团队的定心丸）

| 旧 AgentX 资产 | 新平台的处置 |
|---|---|
| 前端 ClaudeChat / InputPanel / 场景选择器 / SSE 渲染 | **结构基本平移**：改名 AgentChat，场景选择器分组（官方/空间/我的），新增轨迹视图面板 |
| 场景 = 能力声明 + prompt 模板的产品思想 | **升级保留**：装配单字段扩展为 Bundle 描述 |
| AI 生成场景（generate 接口 + 抽屉双模式） | **保留交互，更换引擎**（改由 Creative 模式 Agent 生成） |
| 复核模式（执行 ↔ 复核双模型循环） | **保留**，由 dsh 子代理/双会话实现 |
| 审批交互（ApprovalManager 语义） | **保留语义，更换机制**（tools/* 事件拦截 + 审批桥接插件） |
| FastAPI 分层规范、ResponseUtil、登录态 | **控制面直接复用**（见技术方案） |
| 常驻 ClientPool、OptionsBuilder、hooks、PG transcript | **被 dsh 原生能力替代**：Runner 池 / Bundle 装配 / 拦截事件与沙箱插件 / Session Log 存储插件（详见技术方案迁移映射表） |
