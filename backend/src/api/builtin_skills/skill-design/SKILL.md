# Skill 设计方法

Skill 的读者是另一个 Agent，不是人。写进 Skill 的每一句话，都要让 Agent 读完就知道下一步做什么、做到什么程度算完成。

## 第一步：理解当前任务

- **新建**：用户想把某项工作做成 Skill，或草稿还是空模板 → 先访谈，再出骨架
- **修改**：用户提出了具体改动 → 先读草稿（有附加文件时用 skill_list_files 看一眼目录），只改相关部分，其余原样保留
- **评审**：用户问"写得怎么样""有什么问题" → 按评分表打分并给建议，不修改草稿
- **试用**：用户给出具体任务要求实际执行 → 用 skill_trial 加载最新草稿，按 Skill 调用可用工具完成任务；依据真实结果说明完成情况和阻碍
- **调试**：用户说"调通""修好""再试一次"，或上一轮试用失败后让你继续 → 按下面的调试循环处理
- **答疑**：用户只是提问 → 直接回答，不修改草稿

根据用户意图直接行动；只有缺少会阻断执行的关键信息时才询问。同一句话包含多件事时（例如"改完再测一下"），按先改后测的顺序在同一轮做完。

**调试循环**

1. 确定试用输入：用户本轮给的 → 上一轮试用用过的 → 访谈拿到的真实例子；都没有时设想一个典型输入，并在回复里标明是假设的
2. 用 skill_trial 加载最新草稿，按正文步骤执行，记下第一个出错或卡住的步骤
3. 判断原因：Skill 写法问题（步骤缺失、判断标准不清、引用的文件不存在、脚本报错）才改草稿；输入缺失、环境或权限不足时不改草稿，直接告诉用户需要提供什么
4. 只针对第一个出错的步骤做最小修改，保存后回到第 2 步用同一输入重测
5. 满足任一条件就停下回复：重测通过；已循环 3 轮；需要用户补充信息或做决定；同一问题连续两轮没有改善

只有用户明确要求调通、修好或直接改时才自动循环修改；用户只说"试一下"时，试用发现问题先报告并询问是否修改。

## 第二步：访谈（新建时）

每次最多问 3 个问题，已经知道的不再问。优先问前两个：

1. 这项工作通常由谁发起，在什么情况下发起？用户一般会怎么说？
2. 请给一个最近的真实例子：拿到了什么输入，最后交付了什么？
3. 熟手做这件事时，第一步会先检查什么？
4. 哪些情况必须停下来找人确认，不能自己拿主意？
5. 新人最常在哪里出错？
6. 怎样算做好了？有没有可以参照的成品？

用户说"你看着办"时，按常见做法补全，并在回复里标明哪些是推测、需要用户确认。

## 第三步：写作

出初稿前用 skill_read_guide 读 templates，选最接近的骨架。初稿先给用户看结构，确认后再补全细节。

**元信息**

- name：英文小写加短横线，例如 weekly-report
- title：中文名，简短直白
- description：写成"在……时使用"，带上用户常说的关键词。业务会话靠它判断要不要加载这个 Skill，写不清就不会被用上
- 一个 Skill 只做一件事。范围太大时，建议用户拆成几个

**正文**

- 写明适用和不适用的情况，以及遇到不适用时怎么办
- 写明开始前要确认的输入，缺了怎么向用户要
- 步骤用动词开头，每步写清"做什么"和"做到什么程度算完成"
- 把熟手的判断标准写成具体条件：不写"注意数据质量"，写"缺失超过 10% 的字段先列出来，问用户是否继续"
- 写明必须停下来问人的地方
- 输出要求附一个简短样例
- 正文只放方法；大段资料、清单、模板按第四步拆进 references/、assets/；需要可复用的计算或转换时可写 scripts/
- 需要用到工具、画图或读文件时，先用 skill_read_guide 读 forge-platform，只使用平台确实提供的能力

## 第四步：拆分目录（正文变长，或有资料、模板时）

Skill 是一个目录：SKILL.md 必需，references/、assets/ 和 scripts/ 按需添加。业务会话先只加载 SKILL.md，其他文件要等正文让它读或调用时才会被使用，所以拆出去的内容不占常驻篇幅。

- SKILL.md 只放步骤和判断标准，控制在 300 行以内。超出了，或某部分只在特定情况下才用到，就拆出去
- references/ 放需要时才读的资料：规则清单、术语表、口径说明、检查项。一份文件只讲一个主题，按任务拆分，不要堆成一个大文件
- assets/ 放照着用的东西：报告模板、输出样例、数据格式（json、csv、yaml）
- scripts/ 放确需重复执行的 Python、JavaScript 或 Shell 脚本（.py/.js/.sh）。优先使用标准运行环境；写明输入参数、输出格式及失败处理，不要内嵌凭据。Skill 目录只读，产出写到当前工作目录；单次运行最长 5 分钟，受企业工具策略限制
- 每个文件都要在 SKILL.md 对应步骤里用相对路径写明什么时候读或用，例如"计算指标前，读 references/{口径文件}.md"。正文没提到的文件，Agent 不会知道它存在
- 引用只保持一层：SKILL.md 指向文件，文件之间不再互相引用
- 文件名用英文小写加短横线，例如 metric-definitions.md，看名字就知道内容
- 用 skill_write_file 新建或覆盖文件，skill_delete_file 删除；删除或改名后同步修改正文里的引用
- 维护者上传的文件先用 skill_read_file 读完，再决定直接引用、拆分还是改写
- 脚本写好后用 skill_test_script 试运行，检查退出码、stdout 与 stderr。若隔离环境不可用，不要声称已通过试运行

内容不多时不要硬拆，只有一个 SKILL.md 也是好 Skill。

## 第五步：走查（每次新建或大改后）

用访谈拿到的真实例子，假装自己是执行这个 Skill 的 Agent，从第一步推演到交付，每步检查：

- 这一步需要的信息都有吗？
- 判断标准清楚吗？两个人照着做，结果会一样吗？
- 做完能检验吗？

把卡住的地方列给用户，问清后补进 Skill。没有真实例子时，自己设想一个典型情况来推演，并告诉用户这是假设的例子。

## 第六步：交付前评分

保存前按下表自评，每项 1–3 分。有 1 分的项先改，改不了的写进回复，请用户确认：

| 项目 | 3 分标准 |
|---|---|
| 触发准确 | description 写清了什么情况下用，含用户常用说法 |
| 步骤可执行 | 每步有动作和完成标准，没有含糊、无法照做的说法 |
| 边界清楚 | 有不适用的情况、问人点和缺少输入时的处理 |
| 输出可检验 | 有格式要求和样例，能对照检查 |
| 篇幅得当 | 正文只放方法，长资料和模板拆进 references/、assets/，每个文件都在正文写明何时使用，没有重复 |

保存后调用 skill_validate_draft：errors 必须修正；warnings 逐条判断（包括正文和文件的引用是否对得上），确实不需要的在回复里说明原因。

## 回复用户

- 先用一两句说明结论：改了什么（新建或删除了哪些文件），或评审结果怎样
- 列出走查发现的待确认问题，每条一句
- 试用或调试后说明：用了什么输入、每轮改了什么、最终结果（通过 / 未通过及卡在哪一步）、还需要用户确认什么
- 最后告诉用户怎么试用：在业务会话里输入 /名称，或直接描述任务；试用后把不满意的地方告诉你

评审时用 skill_read_guide 读 examples，指出具体哪句话要怎么改，不说空泛的评价。
